# Feature Chamfer 性能重构失败与五小时返工复盘

> 日期：2026-07-30  
> 严重级别：高  
> 当前状态：`RECOVERY ONLY / PERFORMANCE STOP`  
> 结论：正确效果已恢复，但原计划要求的 Python 高性能路径没有交付。把恢复旧流程描述为任务进展，是本次最严重的判断和沟通错误。

## 1. 用户影响

用户要求在保持旧 Preview → Finalize 效果的前提下，用 Python 路径替代动态 Geometry Nodes 数据编码并显著提速。实际过程先接入了一个错误的快速后端，全部测试 `.blend` 出现重复面、拉伸面和错误封口；随后正式入口退回旧 GN 路径。最终效果恢复，但 Mixed 样本仍约 97–176 秒，性能目标完全没有实现，约五小时未形成用户要求的交付。

## 2. 发生了什么

1. 未先冻结旧输出的严格 oracle，就实现并接入新的紧凑身份路径。
2. 新测试只证明闭合、无零面积、无自交等内部健康指标，错误地把“模型没崩”当成“效果等价”。
3. 新路径在复杂交叉处丢失多重归属，并把越界 station 夹到端点，产生错误或重复 Bridge。
4. 用户用真实 `.blend` 立即发现全部结果不一致，证明自动门禁是假绿。
5. 之后用大量时间追查差异、补旧/新基准并恢复旧正确流程。
6. 恢复后的正式入口仍在后台动态创建数千个 GN 节点；只是把旧两步包装成一次操作，性能没有改善。
7. 又运行了代价很高的矩阵和回归，虽然提高了正确性保护，却没有推进 Python 性能后端。

## 3. 根因

### 3.1 验收顺序颠倒

性能重构的第一门槛本应是“最复杂样本的新旧结果完全等价”，实际却先看通用拓扑健康指标并接正式入口。正确性 oracle 建立得太晚。

### 3.2 同时改变了性能机制和几何语义

目标只是消除动态节点编码，实际还替换了身份表达、边界归属和部分几何重建规则。优化和算法重写混在一起，失败后无法快速判断是哪一层改变了结果。

### 3.3 没有把紧凑身份表达的能力边界当作硬阻断

复杂 Boolean junction 需要同一 Boundary 同时保留多个 owner。紧凑标量只能表达单 owner，这不是调参问题，而是数据模型不具备等价表达能力。第一次发现多 owner 丢失时就应停止该路线。

### 3.4 失败后没有立即切换成旁路原型

用户结果不一致后，正确动作应是：正式入口立刻恢复旧版本，新方案隔离为 `PROTOTYPE`，只在一个 Mixed 样本上继续。实际继续修改正式路径、测试和文档，扩大了返工范围。

### 3.5 把恢复工作和目标进度混为一谈

恢复正确性、补回归和修复事务清理是必要的事故处理，但它们不等于完成 Python 性能后端。状态应始终是 `RECOVERY / PERFORMANCE STOP`，不应接近“做完”的表述。

### 3.6 没有时间盒和路线退出条件

缺少每小时检查和明确 kill criteria。结果是在“也许再修一点能成立”的假设下持续投入，直到五小时后才明确承认核心目标未完成。

## 4. 为什么既有规则没有拦住

- 项目已有 Stop / Go、正式入口验收和独立审计规则，但没有专门约束“性能重构必须同时证明等价与提速”。
- 旧测试覆盖健康性，不覆盖旧/新规范化几何 fingerprint、Chamfer 区域和边界连接的一致性。
- 完整矩阵和完整回归被过早运行；它们验证了错误方向的广度，却没有回答单个最复杂样本是否值得继续。
- 审计发生在大量实现和验证之后，而不是第一个 Mixed 样本失败时。

## 5. 永久预防措施

### 5.1 双硬门槛

任何性能重构只有同时满足以下两项才能离开 `PROTOTYPE`：

1. 结果等价：最复杂代表样本与旧 oracle 的规范化几何、Chamfer Face、边界连接和法线合同一致。
2. 性能有效：同一机器、同一文件、同一参数下，总耗时与分阶段耗时达到预先约定的下降幅度。

只满足一项等同于失败；不允许用“正确但很慢”或“很快但不同”宣称进展。

### 5.2 单样本先行

在 Mixed / Radius 0.01 同时通过等价和性能门槛前：

- 不接正式入口；
- 不跑 10-cell 矩阵；
- 不跑 GUI Undo/Redo；
- 不跑完整回归；
- 不升级阶段状态。

### 5.3 一次只替换一层

先保持旧 FeatureGraph、计划、owner 语义、Boolean 合同和 Bridge/Fill 规则完全不变，只替换动态 GN 数据编码。若必须改变数据模型，先证明它能无损表达 junction 的多 owner，再开始几何运行。

### 5.4 强制退出条件

出现任一条件，路线立即 `STOP`：

- 最复杂样本的旧/新 fingerprint 不一致；
- 任何 Boundary owner 从多值降为单值；
- 需要 fixture 特判、最近距离猜测或越界 station 夹取才能通过；
- 两轮修复后仍无等价结果；
- 一小时内没有可测的阶段耗时下降。

停止后只允许恢复稳定入口和记录证据；继续实验必须放在旁路，不能污染正式 runtime。

### 5.5 每小时状态审计

每 60 分钟必须回答并记录：

1. 正式入口当前是否仍使用目标架构？
2. 最复杂样本是否与旧结果等价？
3. 相比旧路径，哪一阶段减少了多少时间？
4. 当前工作是在推进目标，还是仅在恢复事故？

任何一项无法给出直接证据，立即向用户报告 `STOP`，不得继续数小时后才说明。

### 5.6 状态词隔离

- `RECOVERY`：恢复旧正确行为；不计入性能计划进度。
- `PROTOTYPE`：旁路新后端只在代表样本运行。
- `INTEGRATED`：代表样本等价且达标后才允许接正式入口。
- `VERIFIED`：完整矩阵、回归、GUI 和规格审计通过。
- `ACCEPTED`：用户在 Blender 中确认最终结果。

## 6. 下一次执行的固定顺序

1. 保持当前正确慢路径作为只读 oracle 和安全 fallback。
2. 冻结 Mixed / Radius 0.01 的规范化结果与各阶段耗时。
3. 新建旁路 Python 数据生成原型，只替换动态节点编码，不改几何语义。
4. 每次改动只运行该 Mixed 样本，先比较结果，再记录耗时。
5. 结果不完全一致则立即失败，不进入性能讨论；结果一致但未明显提速也失败。
6. 达到代表样本门槛后才扩展 10-cell，随后才接正式入口、跑 GUI 与完整回归。

## 7. 已落实

- 项目规则已加入性能重构双门槛、单样本先行、`RECOVERY` 隔离和每小时审计。
- 历史计划已标为 `SUPERSEDED`；当前重新规划保持 `PLANNED / PERFORMANCE STOP`，不再把旧路径恢复表述为性能完成。
- 已停止遗留的 Blender 验证进程，避免继续为未通过代表样本的路线消耗时间。

## 8. 未完成事项

- Python 高性能后端仍未实现。
- Mixed ≤ 2 秒和常见样本 ≤ 1 秒的目标仍未达到。
- 在代表样本同时达到结果等价和性能门槛前，不得恢复原计划的完成声明。
